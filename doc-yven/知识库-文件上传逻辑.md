# 知识库文件上传逻辑梳理

> 本文档梳理 Yuxi 工程中知识库文件上传的完整实现链路、核心参数与状态流转。

---

## 一、总体架构

知识库文件上传采用 **"先上传/抓取 → 后入库"** 的两阶段设计，支持三种输入源：

1. **上传文件**（单文件/多文件/拖拽）
2. **上传文件夹**（保留目录结构）
3. **解析 URL**（网页链接抓取）

上传完成后，文件先存入 MinIO 对象存储，用户点击 **"添加到知识库"** 后，后端启动异步三阶段处理管线。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              前端 (Vue3 + Pinia)                             │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐          │
│  │  上传文件/文件夹  │  │    解析 URL      │  │  添加到知识库    │          │
│  └────────┬─────────┘  └────────┬─────────┘  └────────┬─────────┘          │
└───────────┼─────────────────────┼─────────────────────┼────────────────────┘
            │ POST /files/upload  │ POST /files/fetch-url│ POST /databases/{id}/documents
            ▼                     ▼                     ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                         后端 (FastAPI + 异步任务)                            │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │  路由层 (knowledge_router.py)                                         │   │
│  │  • upload_file()      → 存入 MinIO，返回 file_path + content_hash    │   │
│  │  • fetch_url()        → URL 抓取 → 存入 MinIO                        │   │
│  │  • add_documents()    → 创建异步任务 run_ingest()                    │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│                                    │                                        │
│                                    ▼                                        │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │  三阶段处理管线 (KnowledgeBase base.py)                               │   │
│  │  Phase 1: add_file_record()  → 状态: UPLOADED                        │   │
│  │  Phase 2: parse_file()       → 状态: PARSING → PARSED/ERROR_PARSING │   │
│  │  Phase 3: index_file()       → 状态: INDEXING → INDEXED/ERROR_INDEXING│  │
│  └──────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 二、前端实现逻辑

### 2.1 核心组件

| 文件 | 职责 |
|------|------|
| `web/src/components/FileUploadModal.vue` | 上传弹窗 UI，三种模式切换，队列管理 |
| `web/src/apis/knowledge_api.js` | API 封装（`uploadFile`, `fetchUrl`, `addDocuments`） |
| `web/src/stores/database.js` | Pinia Store，`addFiles()` 调用入库 API |

### 2.2 FileUploadModal.vue 核心逻辑

**三种模式切换**：
- `uploadType === 'file'` — 单/多文件上传（`<input type="file" multiple>`）
- `uploadType === 'folder'` — 文件夹上传（`<input webkitdirectory>`）
- `uploadType === 'url'` — URL 解析（文本域输入，每行一个链接）

**上传队列管理**：
- 最大并发数：`maxConcurrent = 10`
- 每个文件独立 XHR 请求，支持进度条 (`onUploadProgress`)
- 文件夹模式使用 `webkitRelativePath` 作为文件名保留目录结构

**OCR 引擎选择**（`ocrEngine` 参数）：
- `none` — 不启用 OCR
- `rapidocr` — RapidOCR
- `mineru` / `mineru-official` — MinerU（本地/官方）
- `pp-structure-v3` — PP-Structure-V3
- `deepseek-ocr` — DeepSeek OCR

**"上传后自动入库"开关**（`autoIndex`）：
- 开启：文件上传成功后立即调用 `addDocuments` 进入三阶段管线
- 关闭：仅上传至 MinIO，用户后续手动触发入库

**同名/同内容检测**：
- 上传前检查 `file.name` 是否已存在于当前知识库文件列表
- 检查 `content_hash` 是否重复，提示用户

### 2.3 前端 API 调用链

```javascript
// 1. 文件上传 → 返回 { file_path, content_hash, ... }
await knowledgeApi.uploadFile(file, { ocr_engine: ocrEngine })

// 2. URL 抓取 → 返回 { file_path, content_hash, ... }
await knowledgeApi.fetchUrl(url, { ocr_engine: ocrEngine })

// 3. 添加到知识库 → 触发后端异步任务
await documentApi.addDocuments(dbId, items, {
  content_type: 'file' | 'url',
  auto_index: true | false,
  ocr_engine: 'none' | 'rapidocr' | ...,
  parent_id: string | null   // 文件夹层级父节点
})
```

## 三、后端路由层实现

### 3.1 路由定义 (`backend/server/routers/knowledge_router.py`)

| 路由 | 方法 | 核心功能 |
|------|------|----------|
| `POST /api/knowledge/files/upload` | `upload_file()` | 接收 UploadFile，写入 MinIO，返回访问 URL 和 hash |
| `POST /api/knowledge/files/fetch-url` | `fetch_url()` | URL 验证 → 下载 HTML → 计算 hash → 上传 MinIO |
| `POST /api/knowledge/databases/{db_id}/documents` | `add_documents()` | 参数校验 → 创建异步任务 `run_ingest()` |

### 3.2 upload_file() 核心逻辑

```python
async def upload_file(file: UploadFile, ocr_engine: str = "none"):
    # 1. 生成唯一对象名: {timestamp}_{uuid4}_{filename}
    # 2. 读取文件内容，计算 SHA-256 content_hash
    # 3. 上传到 MinIO bucket="yuxi-kb-uploads"
    # 4. 返回 { file_path: minio_url, content_hash, size, filename, ocr_engine }
```

**核心参数**：

| 参数名 | 类型 | 说明 |
|--------|------|------|
| `file` | `UploadFile` | FastAPI 上传文件对象 |
| `ocr_engine` | `str` | OCR 引擎标识，默认 `"none"` |
| **返回 `file_path`** | `str` | MinIO HTTP URL，如 `http://minio:9000/yuxi-kb-uploads/xxx.pdf` |
| **返回 `content_hash`** | `str` | 文件内容 SHA-256，用于去重 |

### 3.3 fetch_url() 核心逻辑

```python
async def fetch_url(request: FetchUrlRequest):
    # 1. URL 格式校验（正则 + 白名单 + 私网 IP 拦截）
    # 2. 发送 HTTP GET 请求，限制 max_size=50MB
    # 3. 校验 Content-Type（只允许 text/html, application/pdf 等）
    # 4. 计算 content_hash
    # 5. 上传 MinIO bucket="yuxi-kb-uploads"
    # 6. 返回 { file_path: minio_url, content_hash, size, url }
```

**安全校验机制**（`backend/package/yuxi/knowledge/utils/url_fetcher.py`）：

| 校验项 | 实现 |
|--------|------|
| URL 格式 | 正则匹配 `^https?://` |
| 白名单 | 配置 `URL_FETCH_DOMAIN_WHITELIST`，为空则允许所有 |
| 私网 IP 拦截 | 解析域名后检查是否为 `10.x`, `172.16-31.x`, `192.168.x`, `127.x` |
| Content-Type 限制 | 只允许 `text/html`, `application/pdf`, `text/plain` 等 |
| 文件大小限制 | 默认 50MB，超限时返回 413 |

**核心参数**：

| 参数名 | 类型 | 说明 |
|--------|------|------|
| `url` | `str` | 待抓取的网页链接 |
| `ocr_engine` | `str` | OCR 引擎标识 |
| **返回 `file_path`** | `str` | MinIO URL，文件名为 URL 的 SHA-256 |

### 3.4 add_documents() 核心逻辑

```python
async def add_documents(db_id: str, request: AddDocumentsRequest):
    # 1. 校验知识库存在且非 Dify 只读类型
    # 2. 校验 items 非空
    # 3. 遍历 items，调用 add_file_record() 添加记录（Phase 1）
    # 4. 若 params.auto_index=true，启动异步任务 run_ingest()
    # 5. 返回 { status: "queued", task_id, message }
```

**请求参数** (`AddDocumentsRequest`)：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `items` | `list[str]` | 是 | 文件路径/URL 列表，即 upload_file/fetch_url 返回的 `file_path` |
| `params` | `dict` | 否 | 处理参数 |
| `params.content_type` | `str` | 否 | `"file"` 或 `"url"`，默认 `"file"` |
| `params.auto_index` | `bool` | 否 | 是否自动入库，默认 `true` |
| `params.ocr_engine` | `str` | 否 | OCR 引擎 |
| `params.parent_id` | `str` | 否 | 父文件夹 ID，用于层级结构 |

**响应参数**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | `str` | `"success"` / `"queued"` / `"error"` |
| `task_id` | `str` | 异步任务 ID，用于任务中心追踪 |
| `message` | `str` | 提示信息 |

## 四、后端三阶段处理管线

### 4.1 状态机定义 (`backend/package/yuxi/knowledge/base.py`)

```python
class FileStatus:
    UPLOADED        = "uploaded"         # 初始状态：已添加记录
    PARSING         = "parsing"          # 正在解析
    PARSED          = "parsed"           # 解析完成
    ERROR_PARSING   = "error_parsing"    # 解析失败
    INDEXING        = "indexing"         # 正在入库
    INDEXED         = "indexed"          # 入库完成
    ERROR_INDEXING  = "error_indexing"   # 入库失败
    DONE            = "done"             # 兼容旧版，等价于 INDEXED
    FAILED          = "failed"           # 通用失败
```

### 4.2 Phase 1: add_file_record() — 添加记录

**入口**：`POST /databases/{db_id}/documents` 中遍历 items 调用

**核心逻辑**：

```python
async def add_file_record(self, db_id, item, params=None, operator_id=None):
    # 1. 调用 prepare_item_metadata() 提取文件元数据
    #    - 从 MinIO URL 解析 bucket/object_name
    #    - 获取文件大小、文件名、扩展名
    #    - 生成 file_id (uuid4)
    #    - 计算/复用 content_hash
    # 2. 合并处理参数：
    #    - 知识库级别默认参数 (kb_additional_params)
    #    - 文件级别参数 (file_processing_params)
    #    - 使用 resolve_chunk_processing_params() 合并
    # 3. 设置初始状态: status = UPLOADED
    # 4. 持久化到 metadata 存储（MinIO JSON / PostgreSQL）
    # 5. 返回 file metadata record
```

**核心参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `db_id` | `str` | 知识库 ID |
| `item` | `str` | 文件 MinIO URL 或原始 URL |
| `params` | `dict` | 包含 `content_type`, `ocr_engine`, `auto_index`, `parent_id` 等 |
| `operator_id` | `str` | 操作用户 ID |

**生成的元数据字段**：

| 字段 | 说明 |
|------|------|
| `file_id` | UUID4，文件唯一标识 |
| `path` | MinIO URL |
| `filename` | 原始文件名 |
| `content_hash` | SHA-256 |
| `size` | 文件大小（字节） |
| `extension` | 文件扩展名 |
| `status` | `uploaded` |
| `processing_params` | 合并后的分块/OCR 参数 |
| `created_at` / `created_by` | 创建时间和用户 |

### 4.3 Phase 2: parse_file() — 文件解析

**触发条件**：`auto_index=true` 时，异步任务 `run_ingest()` 自动调用

**核心逻辑**：

```python
async def parse_file(self, db_id, file_id, operator_id=None):
    # 1. 状态校验：只允许从 UPLOADED / ERROR_PARSING / failed 进入
    # 2. 更新状态: PARSING，加入处理队列 _processing_files
    # 3. 调用 Parser.aparse(source=file_path, params=params)
    #    - params 包含 image_bucket="public", image_prefix="{db_id}/kb-images"
    # 4. 解析结果（Markdown 文本）保存到 MinIO bucket="yuxi-kb-parsed"
    #    - 对象名: {db_id}/parsed/{file_id}.md
    # 5. 更新状态: PARSED，记录 markdown_file URL
    # 6. 若失败：状态设为 ERROR_PARSING，记录 error 字段
    # 7. 从处理队列移除
```

**解析器参数** (`params` 透传至 `Parser.aparse`)：

| 参数 | 说明 |
|------|------|
| `ocr_engine` | OCR 引擎选择 |
| `image_bucket` | 图片提取目标 bucket，固定 `"public"` |
| `image_prefix` | 图片前缀，固定 `{db_id}/kb-images` |
| 其他分块参数 | `chunk_method`, `delimiter`, `max_tokens` 等 |

### 4.4 Phase 3: index_file() — 入库索引

**触发条件**：`parse_file()` 成功后，若 `auto_index=true` 则继续执行

**核心逻辑**（抽象方法，具体实现因后端类型而异）：

```python
async def index_file(self, db_id, file_id, operator_id=None, params=None):
    # 1. 状态校验：只允许从 PARSED / ERROR_INDEXING / failed 进入
    # 2. 更新状态: INDEXING
    # 3. 从 MinIO 读取解析后的 Markdown 内容
    # 4. 根据 processing_params 进行分块 (chunking)
    # 5. 调用 Embedding 模型生成向量
    # 6. 写入向量数据库（Milvus / LightRAG / Dify 等）
    # 7. 更新状态: INDEXED
    # 8. 若失败：状态设为 ERROR_INDEXING，记录 error 字段
```

**不同后端的实现**：

| 后端类型 | 实现文件 | 说明 |
|----------|----------|------|
| LightRAG | `implementations/lightrag.py` | 写入 LightRAG 图结构 + 向量索引 |
| Milvus | `implementations/milvus.py` | 写入 Milvus 向量库 |
| Dify | `implementations/dify.py` | 只读，不支持入库 |

### 4.5 异步任务调度

**任务注册**（`add_documents` 路由中）：

```python
from yuxi.services.task_service import tasker

@tasker.task
def run_ingest(task_context: TaskContext, db_id: str, file_ids: list[str], params: dict):
    # 1. 遍历 file_ids
    # 2. 对每个 file_id 依次调用:
    #    - parse_file()   (Phase 2)
    #    - index_file()   (Phase 3, 若 auto_index=true)
    # 3. 更新任务进度到 TaskContext
```

**前端任务追踪**：
- 响应返回 `task_id`，前端在 `taskerStore.registerQueuedTask()` 注册
- 用户可在"任务中心"查看实时进度
- 前端启用自动刷新 (`enableAutoRefresh`) 轮询文件列表状态

## 八、总结

Yuxi 的知识库文件上传采用 **"上传/抓取 → 记录 → 解析 → 索引"** 的四层递进架构：

1. **上传层**：文件/URL 统一存入 MinIO，与业务解耦，返回标准 URL
2. **记录层**：`add_file_record` 创建元数据，状态 `UPLOADED`，支持参数继承（知识库默认 → 文件级 → 请求级）
3. **解析层**：`parse_file` 调用统一 Parser 转为 Markdown，图片提取至 MinIO，状态 `PARSED`
4. **索引层**：`index_file` 按策略分块、Embedding、写入向量库，状态 `INDEXED`

整个流程通过 **异步任务 + 状态机 + 自动刷新** 实现前端无阻塞体验，同时通过 **URL 白名单、私网 IP 拦截、Content-Type 校验、内容 Hash 去重** 保障安全性。
