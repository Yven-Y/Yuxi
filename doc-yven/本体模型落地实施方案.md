# Yuxi 本体（Ontology）落地实施方案

> 整理日期：2026-05-29
> 目标：基于项目现有知识库与知识图谱架构，设计本体（Ontology）子系统，提升实体/关系抽取的一致性和可控性

---

## 一、问题与动机

### 1.1 当前痛点

Yuxi 的知识图谱目前**完全无 Schema 约束**：

- **LightRAG** 自动抽取实体时，LLM 自由决定实体类型和关系类型，导致同一概念出现多种变体（`Person` / `人物` / `person`）
- **Upload 图谱** 的三元组数据无任何格式校验，用户可以随意写实体名和关系类型
- **图谱查询** 时无法按类型精确过滤，前端颜色映射也是硬编码

### 1.2 本体能解决什么

| 维度 | 引入前 | 引入后 |
|------|--------|--------|
| 实体类型 | LLM 自由发挥，类型碎片化 | 受 ontology 约束，类型收敛 |
| 关系类型 | 无约束，同义关系离散 | 受 ontology 约束，关系标准化 |
| 属性校验 | 无 | 可选属性 Schema 校验 |
| 提取质量 | 依赖 prompt 质量 | ontology 引导 + prompt 双保险 |
| 图谱查询 | 无法按类型过滤 | 可按 entity_type / relation_type 精确查询 |
| 前端可视化 | 颜色硬编码 10 种类型 | 根据 ontology 动态配色 |

---

## 二、本体模型设计

### 2.1 最低可行本体（Minimal Viable Ontology）

不做完整 OWL/RDFS，只取工程上最必要的三个概念：

```
Ontology
├── EntityTypes    — 实体类型列表
│   ├── name        — 类型名称 (如 Person / Organization)
│   ├── description — 描述 (如 "表示人类个体")
│   └── properties  — 属性定义 (可选)
│       ├── name       — 属性名 (如 age / birth_date)
│       └── datatype   — 数据类型 (string / integer / date)
│
└── RelationTypes  — 关系类型列表
    ├── name        — 关系名 (如 works_at / located_in)
    ├── description — 描述
    ├── source_type — 允许的头实体类型 (可选，为空则不限制)
    └── target_type — 允许的尾实体类型 (可选，为空则不限制)
```

**格式**（JSON，存于 `additional_params.ontology`）：

```json
{
  "entity_types": [
    {
      "name": "Person",
      "description": "表示人类个体",
      "properties": [
        {"name": "age", "datatype": "integer"},
        {"name": "birth_date", "datatype": "date"}
      ]
    },
    {
      "name": "Organization",
      "description": "表示组织、公司、机构",
      "properties": [
        {"name": "founded_year", "datatype": "integer"},
        {"name": "location", "datatype": "string"}
      ]
    }
  ],
  "relation_types": [
    {
      "name": "works_at",
      "description": "表示某人在某组织工作",
      "source_type": "Person",
      "target_type": "Organization"
    },
    {
      "name": "located_in",
      "description": "表示某实体位于某地",
      "source_type": "Organization",
      "target_type": "Location"
    }
  ]
}
```

### 2.2 为什么是这个粒度的设计

- **不做 OWL/DL 推理**：知识库场景不需要类层次推理（subClassOf）、不相交检测等重型语义，当前阶段做就是过度设计
- **属性定义可选**：大部分 LLM 抽取场景只关心实体类型和关系类型，属性是锦上添花
- **source_type/target_type 可选**：约束了更好，不约束也允许自由关系
- **按知识库独立**：不同知识库的领域本体不同（医学、法律、金融），每个知识库一份 ontology

## 三、存储方案

### 3.1 数据存储位置

```
PostgreSQL KnowledgeBase 表
  └── additional_params (JSONB)
       └── "ontology": {
             "entity_types": [...],
             "relation_types": [...]
           }
```

**选择理由**：
- `additional_params` 已经是项目约定的扩展字段，不需要新增数据库列
- JSONB 天然适合 Schema 类数据的存储和查询
- 随知识库 CRUD 一并持久化，无需独立的 ontology 表

### 3.2 生命周期

| 操作 | 行为 |
|------|------|
| 创建知识库 | 可选传入 ontology，不传则继续自由抽取（向后兼容） |
| 更新知识库 | 可修改 ontology，修改后**已入库的旧实体/关系不受影响** |
| 删除知识库 | ontology 随 additional_params 一并删除 |
| 查询 | 返回完整 ontology |

## 四、集成点设计

### 4.1 LightRAG 实体抽取集成

**目标**：将 ontology 传给 LightRAG 的 `addon_params`，引导 LLM 抽取时遵循类型约束。

**现状**（`implementations/lightrag.py` 第 146-154 行）：

```python
metadata = self.databases_meta[db_id].get("metadata", {}) or {}
addon_params = {}
if isinstance(metadata.get("addon_params"), dict):
    addon_params.update(metadata.get("addon_params", {}))
# ... 处理 language
rag = LightRAG(addon_params=addon_params, ...)
```

**改造**：在构建 `addon_params` 时注入 ontology：

```python
# 注入 ontology 到 addon_params
ontology = metadata.get("ontology")
if ontology and isinstance(ontology, dict):
    entity_types = ontology.get("entity_types", [])
    relation_types = ontology.get("relation_types", [])
    if entity_types:
        # 透传给 LightRAG 用于实体抽取引导
        addon_params["entity_types"] = [et["name"] for et in entity_types]
    if relation_types:
        addon_params["relation_types"] = [rt["name"] for rt in relation_types]
```

> **注意**：`addon_params` 的具体 key 名取决于 `lightrag-hku` 库的接口约定。如果该库目前不支持 `entity_types` / `relation_types` 参数，替代方案是修改 LightRAG 的 entity extraction prompt，将 ontology 作为 system prompt 的一部分注入。这需要 fork 或 monkeypatch LightRAG 的 prompt 模板。

**回退方案**（如果 LightRAG 库不原生支持 ontology 参数）：

```python
# 将 ontology 注入到自定义 prompt 中
from lightrag.prompt import PROMPTS
ontology_prompt = build_ontology_prompt(ontology)
PROMPTS["entity_extraction"] = ontology_prompt + PROMPTS["entity_extraction"]
```

### 4.2 Upload 图谱集成

**目标**：在用户上传三元组时，校验实体类型和关系类型是否匹配 ontology。

**改造点**（`upload_graph_service.py` 的 `jsonl_file_add_entity()`）：

```python
def _validate_entity_against_ontology(self, entity_name: str, entity_type: str, 
                                       ontology: dict) -> bool:
    """校验实体类型是否在 ontology 允许范围内"""
    allowed_types = {et["name"] for et in ontology.get("entity_types", [])}
    if not allowed_types:  # 没有 ontology 则不校验
        return True
    return entity_type in allowed_types

def _validate_relation_against_ontology(self, head_type: str, rel_type: str, 
                                         tail_type: str, ontology: dict) -> bool:
    """校验关系类型是否符合 ontology 约束"""
    relation_types = ontology.get("relation_types", [])
    if not relation_types:  # 没有 ontology 则不校验
        return True
    for rt in relation_types:
        if rt["name"] != rel_type:
            continue
        # 检查 source_type / target_type 约束
        if rt.get("source_type") and rt["source_type"] != head_type:
            return False
        if rt.get("target_type") and rt["target_type"] != tail_type:
            return False
        return True
    return False  # 关系类型不在 ontology 定义中
```

**交互策略**：
- **严格模式**（默认）：不合规的三元组拒绝入库，返回具体错误信息
- **宽松模式**：警告但不阻断，未知类型自动加入 ontology（渐进式构建本体）

### 4.3 图谱查询集成

**目标**：利用 ontology 提供类型化的查询能力。

**改造点**（`GraphAdapter.query_nodes()` 的 `GraphQueryConfig`）：

```python
# 在 GraphQueryConfig 中新增可选字段
class GraphQueryConfig:
    entity_type: str = None      # 按实体类型过滤
    relation_type: str = None    # 按关系类型过滤
    # ... 现有字段
```

**查询行为**：
- LightRAG 适配器：用 `entity_type` 过滤 Neo4j 标签
- Upload 适配器：用 `entity_type` 过滤节点属性（如果 Upload 图也开始记录类型）

> Upload 图当前不记录实体类型，需要同步改造 `txt_add_vector_entity()` 来写入类型数据（见 九 节）。

### 4.4 Agent 中间件集成

**目标**：Agent 在写入知识图谱时自动遵循 ontology。

**改造点**（`KnowledgeBaseMiddleware`）：


或者在 `query_kb` 工具的描述中自动嵌入实体类型列表，帮助 Agent 理解可用的查询维度。

## 五、API 设计

### 5.1 本体 CRUD

在知识库管理 API 中扩展 ontology 子资源：

```http
PUT    /api/knowledge/databases/{db_id}/ontology     # 设置或更新本体
GET    /api/knowledge/databases/{db_id}/ontology     # 获取本体
DELETE /api/knowledge/databases/{db_id}/ontology     # 删除本体（恢复自由模式）
```

**PUT 请求体**：

```json
{
  "entity_types": [
    {"name": "Person", "description": "人类", "properties": []}
  ],
  "relation_types": [
    {"name": "works_at", "description": "工作于", "source_type": "Person", "target_type": "Organization"}
  ]
}
```

**响应码**：

| 状态 | 含义 |
|------|------|
| 200 | 更新成功，返回完整 ontology |
| 204 | 删除成功 |
| 400 | ontology 格式非法 |
| 404 | 知识库不存在 |

### 5.2 本体验证

```http
POST   /api/knowledge/databases/{db_id}/ontology/validate   # 验证三元组是否符合本体
```

请求：
```json
{
  "triples": [
    {"head": "张三", "head_type": "Person", "relation": "works_at", "tail": "阿里", "tail_type": "Organization"}
  ]
}
```

响应：
```json
{
  "valid": true,
  "violations": []
}
```

### 5.3 创建知识库时传入本体

**扩展 `POST /api/knowledge/databases` 的 `additional_params`**：

```json
{
  "additional_params": {
    "chunk_preset_id": "general",
    "language": "Chinese",
    "ontology": {
      "entity_types": [...],
      "relation_types": [...]
    }
  }
}
```

路由层无需修改（`**additional_params` 自动解包），只需在 Manager 层提取 `ontology` 字段单独存储。

### 6.2 模板解析与使用

```python
from yuxi.utils.common import deep_merge

def get_ontology_template(template_id: str) -> dict | None:
    """根据模板 ID 获取完整的 ontology 定义（合并基础默认值）"""
    if template_id not in ONTOLOGY_TEMPLATE_IDS:
        return None
    template_def = _TEMPLATE_DEFAULTS.get(template_id, {})
    return deep_merge(_BASE_ONTOLOGY, template_def)

def get_ontology_template_options() -> list[dict]:
    """返回前端模板选择器所需的选项列表"""
    return [
        {
            "value": tid,
            "label": ONTOLOGY_TEMPLATE_DESCRIPTIONS.get(tid, tid),
        }
        for tid in sorted(ONTOLOGY_TEMPLATE_IDS)
    ]

def normalize_template_id(template_id: str | None) -> str:
    """标准化模板 ID，非法值 fallback 到 general"""
    if not template_id or template_id not in ONTOLOGY_TEMPLATE_IDS:
        return ONTOLOGY_TEMPLATE_GENERAL
    return template_id
```

### 6.3 模板与用户自定义的关系

模板是**复制即独立**的模式（copy-on-select），不是实时引用：

```
用户创建知识库 → 选择模板 "医疗" 
  → _TEMPLATE_DEFAULTS["medical"] 的 ontology 拷贝到 additional_params.ontology
  → 用户之后可以自由修改这份 ontology（增删类型、调整属性）
  → 原始模板不变，用户修改不影响模板
```

**关键设计决策**（与 chunk presets 保持一致）：
- 模板定义存于 Python 代码中，而非数据库。这样方便版本控制、Code Review、CI/CD
- 新增模板只需在 `_TEMPLATE_DEFAULTS` 中添加一个条目 + 前端选项列表，无需数据迁移
- 模板只负责**初始值**，用户修改后的 ontology 存在知识库的 `additional_params` 中

## 七、复杂数据处理策略

本节针对用户可能遇到的大规模、复杂本体场景，提供分层处理方案。

### 7.1 大本体（100+ 实体类型）

**问题**：ontology JSONB 膨胀，API 响应慢，前端编辑器渲染卡顿。

**分层策略**：

| 层级 | 阈值 | 处理方式 |
|------|------|---------|
| **小型本体** | ≤ 30 个实体类型 | 全量加载，前端表格渲染无压力 |
| **中型本体** | 30~100 个实体类型 | 前端分页 + 虚拟滚动 + 搜索过滤，后端全量返回 |
| **大型本体** | > 100 个实体类型 | 后端分页返回 + 前端按需加载 + 仅展开当前编辑的类型 |

**API 分页支持**（`GET /api/knowledge/databases/{db_id}/ontology`）：

```json
// 请求
GET /api/knowledge/databases/{db_id}/ontology?entity_page=1&entity_size=50

// 响应
{
  "entity_types": [ ... ],        // 当前页
  "relation_types": [ ... ],      // 全量返回（关系类型通常不多）
  "pagination": {
    "entity_total": 230,
    "entity_page": 1,
    "entity_size": 50,
    "entity_pages": 5
  }
}
```

**性能基准**：
- JSONB 字段 100KB 以内 PostgreSQL 读写性能无损（100 个实体类型 + 100 个关系类型大约 20-30KB）
- 超过 500KB 考虑压缩存储或拆分子字段，但实际场景极少达到

### 7.2 类型层次（父类继承）

**问题**：真实领域的实体有层级关系，"主任医师"是"医生"的子类，"医生"是"人员"的子类。当前设计不支持。

**方案**：在 `entity_type` 上增加可选的 `parent_type` 字段 —— **单继承，不递归推理**：

```json
{
  "entity_types": [
    {"name": "Person", "description": "人类个体", "parent_type": null, "properties": [
      {"name": "age", "datatype": "integer"}
    ]},
    {"name": "Doctor", "description": "医生", "parent_type": "Person", "properties": [
      {"name": "specialty", "datatype": "string"}
    ]},
    {"name": "Surgeon", "description": "外科医生", "parent_type": "Doctor", "properties": [
      {"name": "operation_count", "datatype": "integer"}
    ]}
  ]
}
```

**语义约定**（不实现推理，仅用于验证和查询）：
- **属性继承**：`Surgeon` 的有效属性 = 自身 properties + `Doctor` 的 properties + `Person` 的 properties（纯展示，不做 OWL 推理）
- **关系匹配**：如果关系定义 `source_type = "Person"`，则 `Person` 及其所有子孙类型都可通过校验（`is_type_or_descendant_of(entity_type, relation_source_type)`)
- **前端展示**：类型选择器按树形展示，支持展开/折叠

```python
def is_type_or_descendant_of(entity_type: str, target_type: str, 
                              entity_types: list[dict]) -> bool:
    """检查 entity_type 是否等于 target_type 或是其子孙类型"""
    if entity_type == target_type:
        return True
    # 构建 parent 映射
    parent_map = {et["name"]: et.get("parent_type") for et in entity_types}
    current = entity_type
    while current in parent_map:
        current = parent_map[current]
        if current == target_type:
            return True
        if current is None:
            break
    return False
```

**为什么不做完整推理**：
- 多继承（`TeachingHospital` 既是 `Hospital` 也是 `School`）需要完整 OWL 推理引擎，引入复杂度远超收益
- 单继承 + 简单遍历足够覆盖 95% 的实际本体建模场景
- 保留 `parent_type` 字段为未来升级到 OWL 推理预留数据基础

### 7.3 扩展属性模型

**问题**：真实场景中属性有复杂约束 —— 枚举值、必填、多值、引用其他实体、嵌套对象等。

**属性定义扩展**（保留旧格式兼容，新格式增强）：

```json
// 简单格式（完全兼容现有设计）
{"name": "age", "datatype": "integer"}

// 完整格式
{
  "name": "gender",
  "datatype": "enum",
  "enum_values": ["男", "女", "其他"],
  "required": true,
  "description": "患者性别"
}

// 引用格式（属性值指向其他实体）
{
  "name": "hospital",
  "datatype": "reference",
  "reference_type": "Organization",
  "description": "所属医院"
}

// 多值格式
{
  "name": "aliases",
  "datatype": "list<string>",
  "description": "别名列表"
}
```

**支持的 datatype**：

| datatype | 说明 | 校验方式 |
|----------|------|---------|
| `string` | 字符串 | 无特殊校验 |
| `integer` | 整数 | `isinstance(val, int)` |
| `float` | 浮点数 | `isinstance(val, (int, float))` |
| `boolean` | 布尔值 | `isinstance(val, bool)` |
| `date` | 日期字符串 | `dateutil.parser.parse(val)` |
| `enum` | 枚举值 | `val in enum_values` |
| `reference` | 引用其他实体 | 跨节点存在性校验（可选） |
| `list<string>` 等 | 多值列表 | `isinstance(val, list)` + 元素类型校验 |

**渐进式增强**：简单格式自动解释为 `{"name": xx, "datatype": "string", "required": false}`，无需数据迁移。

### 7.4 高量级本体验证（性能优化）

**场景**：上传 10 万条三元组，每条都要校验 ontology，O(n²) 的 `for rt in relation_types` 遍历不可接受。

**优化方案**：

```python
class OntologyValidator:
    """高性能本体验证器 —— 构建索引，O(1) 查询"""
    
    def __init__(self, ontology: dict):
        # 构建哈希索引
        self._entity_type_set: set[str] = {
            et["name"] for et in ontology.get("entity_types", [])
        }
        # 关系索引：{rel_name: {source_type, target_type}}
        self._relation_index: dict[str, dict] = {}
        for rt in ontology.get("relation_types", []):
            self._relation_index[rt["name"]] = {
                "source_type": rt.get("source_type"),
                "target_type": rt.get("target_type"),
            }
        # 父类映射（用于类型层次校验）
        parent_map = {et["name"]: et.get("parent_type")
                       for et in ontology.get("entity_types", [])}
        self._descendant_cache: dict[str, set[str]] = {}  # 懒加载缓存
    
    def validate_entity_type(self, entity_type: str) -> bool:
        """O(1)"""
        return entity_type in self._entity_type_set or not self._entity_type_set
    
    def validate_relation(self, head_type: str, rel_type: str, tail_type: str) -> bool:
        """O(1)"""
        rt = self._relation_index.get(rel_type)
        if rt is None:
            return not self._relation_index  # 无 ontology 则通过
        # source_type / target_type 约束检查
        src_ok = (rt["source_type"] is None or 
                  self._is_descendant_or_self(head_type, rt["source_type"]))
        tgt_ok = (rt["target_type"] is None or 
                  self._is_descendant_or_self(tail_type, rt["target_type"]))
        return src_ok and tgt_ok
    
    def validate_batch(self, triples: list[dict]) -> list[dict]:
        """批量校验 —— 一次遍历，返回违规列表"""
        violations = []
        for i, triple in enumerate(triples):
            h_type = triple.get("head_type", "unknown")
            t_type = triple.get("tail_type", "unknown")
            rel = triple.get("relation", "")
            
            if not self.validate_entity_type(h_type):
                violations.append({"index": i, "field": "head_type", 
                                   "value": h_type, "reason": "unknown entity type"})
            if not self.validate_entity_type(t_type):
                violations.append({"index": i, "field": "tail_type",
                                   "value": t_type, "reason": "unknown entity type"})
            if not self.validate_relation(h_type, rel, t_type):
                violations.append({"index": i, "field": "relation",
                                   "value": rel, "reason": f"invalid for {h_type}->{t_type}"})
        return violations
```

**批量上传时的校验流程**（在 `jsonl_file_add_entity` 中）：

```
JSONL 文件 (10万行)
  → 流式读取（不一次性加载全部）
    → 分批校验（每批 1000 条，调用 validate_batch）
      → 记录违规行号和原因
        → 合规的批次写入 Neo4j (execute_write)
          → 返回：成功数 + 违规详情列表
```

### 7.5 本体版本与迁移

**场景**：知识库运行一段时间后 ontology 变更（添加新类型、修改关系约束），旧图谱数据如何与新 ontology 共存。

**方案**：轻量版本号 + 数据标注，不做在线迁移：

```json
{
  "entity_types": [...],
  "relation_types": [...],
  "meta": {
    "version": 3,
    "updated_at": "2026-06-15T10:30:00Z",
    "changelog": "新增 EntityType: Supplier；修改 works_at 的 source_type 约束"
  }
}
```

| 策略 | 做法 |
|------|------|
| **读取** | 旧图谱数据不受影响，图谱节点上标记 `ontology_version` 属性（写入时记录） |
| **校验** | Upload 新数据按最新 ontology 校验；已入库数据不做回校验 |
| **查询** | 图谱查询时可按 `ontology_version` 过滤，方便查看哪些节点来自旧版本 ontology |
| **迁移** | 不做自动迁移。提供手动触发按钮，由用户决定何时重新抽取/重新校验旧数据 |

**关键原则**：ontology 只向前约束新数据，不破坏旧数据。这避免了分布式数据迁移的一致性难题。

### 7.6 前端处理大 ontology 的 UI 策略

| 场景 | 策略 |
|------|------|
| 实体类型列表 > 50 个 | 虚拟滚动（vue-virtual-scroller）+ 顶部搜索过滤 |
| 关系类型列表 > 100 个 | 按 source_type 分组折叠，展开/收起 |
| 全量 ontology 加载耗时 > 2s | 骨架屏 + 分页加载（先加载前 50 个实体类型，滚动到底部自动加载更多） |
| 本体预览图节点 > 200 个 | G6 使用 WebGL 渲染器 + 节点聚合（同类型节点折叠为一个大节点） |
| 编辑时即时验证 | debounce 300ms + Web Worker 中校验（避免阻塞 UI 线程） |

## 九、Upload 图谱的类型化改造

### 9.1 当前问题

Upload 图谱的三元组写入（`upload_graph_service.py` 第 175-192 行）：

```cypher
MERGE (h:Entity:Upload {name: $h_name})
MERGE (t:Entity:Upload {name: $t_name})
MERGE (h)-[r:RELATION {type: $r_type}]->(t)
```

这里 `h` 和 `t` 当前只存了 `name`（和 extras props），没有存 **实体类型**。

### 9.2 改造方案

**JSONL 输入格式扩展**（向后兼容）：

```jsonl
{"h": "张三", "h_type": "Person", "r": "works_at", "t": "阿里巴巴", "t_type": "Organization"}
```

**Cypher 写入改造**：

```cypher
MERGE (h:Entity:Upload {name: $h_name})
SET h.entity_type = $h_type, h += $h_props
MERGE (t:Entity:Upload {name: $t_name})
SET t.entity_type = $t_type, t += $t_props
MERGE (h)-[r:RELATION {type: $r_type}]->(t)
```

**关键点**：
- `h_type` / `t_type` 可选，不传则设为 `"unknown"`
- 新增 `entity_type` 属性到节点
- 前端图谱组件可以基于 `entity_type` 做动态配色，不再硬编码

## 十二、风险与边界

| 风险 | 缓解方案 |
|------|---------|
| LightRAG 库不支持 ontology 参数 | 降级为 Prompt 注入方案 |

| 过度设计 | 严格遵循 Phase 渐进策略，每阶段验证后再继续 |

- OWL 逻辑推理（subClassOf、transitive property、disjointWith 等）
- 跨知识库的 ontology 对齐 / 融合
- SPARQL 查询接口
- 自动从数据推理出 ontology（ontology learning）
- RDF/OWL 序列化导出
- 多继承类型体系
