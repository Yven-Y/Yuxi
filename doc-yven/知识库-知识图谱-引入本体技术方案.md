# 知识库-知识图谱-引入本体技术方案

> 创建日期：2026-05-29
> 状态：草案

## 一、目标与范围

### 1.1 目标

将本体模型（Ontology）引入 Yuxi 的知识图谱构建管道，使 LLM 在实体/关系抽取时受预定义本体约束，从而：

- **提升标签一致性**：同一类实体使用统一的本体类型，消除同义混用
- **支持层次推理**：通过本体继承关系，父类查询可召回所有子类节点
- **过滤不合理关系**：用本体关系约束校验 LLM 抽取的三元组合理性
- **增强可解释性**：每个标签在本体中有明确定义和位置

### 1.2 范围

| 模块 | 改动范围 |
|------|---------|
| 本体管理 | 新增：本体 CRUD、本体与知识库绑定 |
| LightRAG 抽取管道 | 改造：注入本体约束 prompt，后校验 |
| 图谱查询 | 改造：本体层级感知的查询适配 |
| 前端 | 新增：本体管理页面；改造：知识库创建/配置页 |

**不在范围内**：
- 不替换 LightRAG 库本身
- 不改动手动 Upload 图谱管道（Upload 路径已硬编码标签，本体化留作后续）

## 三、数据模型设计

### 3.1 本体定义存储（PostgreSQL 新增表）

```sql
-- 本体目录：一个用户可以创建多个本体
CREATE TABLE ontology_catalog (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        VARCHAR(255) NOT NULL,
    description TEXT,
    user_id     VARCHAR(255),
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now()
);

-- 实体类型树：扁平存储，通过 parent_id 维护层级
CREATE TABLE ontology_entity_type (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    catalog_id  UUID NOT NULL REFERENCES ontology_catalog(id) ON DELETE CASCADE,
    name        VARCHAR(255) NOT NULL,          -- 如 "公司"
    parent_id   UUID REFERENCES ontology_entity_type(id),  -- NULL 表示根节点
    description TEXT,
    sort_order  INT DEFAULT 0,
    created_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE (catalog_id, name, parent_id)        -- 同一目录下同层级名唯一
);

-- 关系类型：允许的实体间关系定义
CREATE TABLE ontology_relation_type (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    catalog_id    UUID NOT NULL REFERENCES ontology_catalog(id) ON DELETE CASCADE,
    name          VARCHAR(255) NOT NULL,        -- 如 "供职于"
    source_type_id UUID NOT NULL REFERENCES ontology_entity_type(id),
    target_type_id UUID NOT NULL REFERENCES ontology_entity_type(id),
    description   TEXT,
    created_at    TIMESTAMPTZ DEFAULT now(),
    UNIQUE (catalog_id, name, source_type_id, target_type_id)
);

-- 知识库与本体绑定
ALTER TABLE knowledge_base
ADD COLUMN ontology_catalog_id UUID REFERENCES ontology_catalog(id);
```

### 3.2 Neo4j 中的标签变更

**当前**：LightRAG 给实体打 `Entity` + `kb_{db_id}` 标签。

**改造后**：额外打上本体层级标签路径，如：

```
当前:  (n:Entity:kb_abc123 {name: "苹果"})
改造后: (n:Entity:Ontology__Organization__Company:kb_abc123 {name: "苹果"})
```

标签命名约定：`Ontology__{Level1}__{Level2}__...`，例如：

| 本体路径 | Neo4j 标签 |
|---------|-----------|
| 组织/公司/科技企业 | `Ontology__组织__公司__科技企业` |
| 人物 | `Ontology__人物` |
| 自然物/水果 | `Ontology__自然物__水果` |

**层级查询优势**：
```cypher
-- 查所有"组织"及其子类（包含公司、科技企业）
MATCH (n) WHERE any(label IN labels(n) WHERE label STARTS WITH 'Ontology__组织')
RETURN n
```

## 四、核心流程设计

### 4.1 本体定义流程

```
用户创建本体目录
  → 定义实体类型树 (树形结构，支持层级)
  → 定义关系类型 (source_type → target_type，可选)
  → 绑定本体到知识库 (knowledge_base.ontology_catalog_id = catalog.id)
```

**前端交互**：树形编辑器 + 拖拽；关系类型以 source/target 选择器 + 连线方式配置。

### 4.2 实体抽取流程（改造 LightRAG 管道）

改造点位于 `LightRagKB.index_file()` → `rag.ainsert()` 调用链。两个策略：

#### 策略 A：Prompt 注入（推荐，改动最小）

在调用 `rag.ainsert()` 之前，**不修改 LightRAG 库**，而是利用 LightRAG 的 `addon_params` 机制（若支持）或通过 **LLM function hook** 注入本体的系统提示。

**关键改造**：`_create_kb_instance()` 中，如果知识库绑定了本体，则在 `addon_params` 中传入本体描述文本：

```python
# 新增参数
addon_params["entity_type_constraints"] = ontology_to_prompt_text(catalog)
# 生成类似：
# "只能使用以下实体类型：组织\公司\科技企业, 人物, 自然物\水果, ...
#  关系类型：供职于(人物→组织\公司), 生产(组织\公司→产品), ..."
```

然后在 LightRAG 初始化时将自定义的 entity_extraction prompt 传入。

**影响范围**：
- `LightRagKB._create_kb_instance()` — 注入本体参数
- `backend/package/yuxi/ontology/prompt_builder.py` — 本体→prompt 转换

#### 策略 B：后置校验 + 矫正（兜底）

如果 LightRAG 不支持直接注入自定义 prompt，则在 `_ensure_doc_processed()` 之后增加本体合规校验步骤：

```python
# 在 ainsert 完成后
await rag.ainsert(...)
await self._ensure_doc_processed(rag, file_id)

# 新增：本体合规校验
if ontology_catalog_id:
    await self._validate_ontology_compliance(rag, db_id, ontology_catalog_id)
```

`_validate_ontology_compliance()` 逻辑：
1. 从 Neo4j 读取本次入库的新增节点
2. 用 LLM 对每个实体的标签做本体对齐（映射到最匹配的本体类型）
3. 更新 Neo4j 中不对齐的节点标签
4. 记录拒绝的不合理关系

### 4.3 查询流程改造

改造 `LightRAGGraphAdapter` 的查询方法：

```python
# backend/package/yuxi/knowledge/graphs/adapters/lightrag.py

class LightRAGGraphAdapter(BaseNeo4jAdapter):
    
    async def query_nodes(self, config: GraphQueryConfig, ontology_ids: list[str] = None):
        """查询节点，支持本体层级展开"""
        if ontology_ids:
            # 将本体 ID 展开为 Neo4j 标签前缀列表
            label_prefixes = await self._expand_ontology_labels(ontology_ids)
            # 构建 Cypher：WHERE any(label IN labels(n) WHERE label STARTS WITH ...)
        return await super().query_nodes(config)
```

## 八、风险与应对

| 风险 | 应对 |
|------|------|
| **LightRAG 库不支持自定义 entity_extraction prompt** | 启用策略 B（后置校验矫正），同时提 issue/pr 给 LightRAG |
| **本体类型过多导致 prompt token 爆炸** | 只注入顶层 2-3 级本体，深层类型用 LLM 推断 |
| **现有 LightRAG 数据无本体标签，查询不兼容** | 查询时优先用 `kb_{db_id}` 标签回退，无本体时不展开 |
| **LLM 输出格式不稳定，标签可能不在本体中** | validator 做二次矫正，兜底映射到最近的本体类型 |
| **本体变更后历史数据标签过期** | 一期不做自动迁移；本体编辑时提示影响范围，后续手动触发重索引 |

---

## 九、验收标准

1. 能成功创建、编辑、删除本体定义（含层级结构）
2. 知识库能绑定本体，绑定后入库的实体标签符合本体约束
3. 同一类实体的标签一致性相比于无本体时有可量化的提升（如相同实体被标注为不同类型的情况减少 80%+）
4. 图谱查询支持按本体类型和层级的过滤
5. 不影响未绑定本体的知识库的原有行为

## 十、主流方案对比

当前业界在 RAG 知识图谱中引入本体的主流方案有 6 种，以下从架构复杂度、精度、成本、与 Yuxi 兼容性四个维度逐一对比。

### 10.1 六大方案总览

| 方案 | 核心思路 | 代表实践 |
|------|---------|---------|
| **A. Prompt 约束抽取**（当前方案） | 本体注入 LLM prompt，约束抽取输出 | LangChain + Ontology、Neo4j GraphRAG（社区版） |
| **B. LLM Structured Output** | 利用 Function Calling / JSON Schema 让 LLM 返回严格类型 | OpenAI Structured Outputs、Instructor |
| **C. 微调专用抽取模型** | 训练 NER/RE 模型，直接输出本体类型 | GLiNER、NuNER、自训练 BERT 系模型 |
| **D. 两阶段：抽取→映射** | 先自由抽取，再 LLM 或向量相似度映射到本体 | Microsoft GraphRAG 企业版思路、AllenNLP |
| **E. 原生语义推理引擎** | 用 OWL/RDF + 推理机 (HermiT/Pellet) 做本体推理 | Palantir Foundry Ontology、Apache Jena |
| **F. 仅查询层本体增强** | 不改抽取管道，只在查询时按本体展开/重写 | Neo4j GraphRAG（标签索引增强版） |

### 10.2 逐方案详细对比

#### 方案 A：Prompt 约束抽取（当前方案）

**做法**：在 LLM 实体抽取 prompt 中注入本体类型树和关系约束，让 LLM 在抽取时直接将实体映射到本体类型。

```
Prompt 示例：
"你是一个实体抽取器。请从文本中抽取实体，每个实体必须归类到以下类型之一：
  - 人物
  - 组织\公司
  - 组织\政府机构
  - 产品\软件
  - 地点\城市
不允许使用上述列表之外的类型。"
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐⭐ 低。不引入新组件，只改 prompt |
| 抽取精度 | ⭐⭐⭐ 中等。受 LLM 能力影响，复杂本体下可能漏分或误分 |
| 运行成本 | ⭐⭐⭐⭐ 低。无额外 LLM 调用 |
| Yuxi 兼容性 | ⭐⭐⭐⭐⭐ 高。不改 LightRAG 库，加 addon_params |

**优点**：实现最快，与现有架构无缝衔接，不增加延迟。
**缺点**：LLM 不是 100% 遵守 prompt 约束；本体类型超过 ~30 个后 prompt 过长，命中率下降。

---

#### 方案 B：LLM Structured Output（JSON Schema / Function Calling）

**做法**：利用 LLM 的结构化输出能力，定义 JSON Schema 或 Function 让 LLM 强制输出预定义枚举值。

```json
{
  "type": "object",
  "properties": {
    "entities": [{
      "name": "string",
      "type": { "enum": ["人物", "组织.公司", "产品.软件"] }
    }]
  }
}
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐⭐ 低。但需要 LightRAG 支持自定义 JSON Schema |
| 抽取精度 | ⭐⭐⭐⭐ 高。JSON Schema 约束比纯文本 prompt 更强 |
| 运行成本 | ⭐⭐⭐ 中等。structured output 模式 token 消耗略高 |
| Yuxi 兼容性 | ⭐⭐ 低。LightRAG 库内置 prompt 不支持 JSON Schema 覆盖，需 fork 修改 |

**优点**：输出格式严格，几乎不会出现本体外类型；精度比纯 prompt 高。
**缺点**：需要修改 LightRAG 内部的 entity_extraction prompt 模板（当前通过 `addon_params` 只注入额外参数，不直接覆盖系统 prompt）。LightRAG v1.x 不支持 `response_format` 参数透传。

---

#### 方案 C：微调专用抽取模型

**做法**：不依赖 LLM，训练一个小型 NER 模型（如 GLiNER、BERT-NER），让它直接从文本中抽取实体并分类为本体类型。

```
流程：文本 → Fine-tuned NER Model → [(实体, 本体类型), ...]
                        ↓
              无需额外 LLM 调用
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐⭐⭐⭐ 高。需要训练管线、标注数据、模型部署 |
| 抽取精度 | ⭐⭐⭐⭐⭐ 高（在训练领域内）→ ⭐⭐ 低（泛化到新领域） |
| 运行成本 | ⭐⭐⭐⭐⭐ 极低。推理只需 GPU/CPU，无 LLM token 费用 |
| Yuxi 兼容性 | ⭐ 极低。完全替换 LightRAG 的抽取管道，等于自建一套 |

**优点**：推理速度快、成本极低；在自己的训练域内精度极高。
**缺点**：需要大量标注数据（至少数千条）；换了本体就要重新标注和训练；无法利用 LLM 对复杂语义的理解能力。**不适合 Yuxi 这种通用知识库平台**，更适合垂直领域专有部署。

---

#### 方案 D：两阶段：抽取→映射

**做法**：保持 LightRAG 自由抽取不变，抽出实体后，用第二个 LLM 调用（或向量相似度）将自由标签映射到本体类型。

```
流程：
文档 → LightRAG 抽取 (自由标签) → 第二阶段对齐 → 本体标签
      "科技企业", "公司"            LLM/向量映射      → "组织/公司"
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐⭐⭐ 中高。新增映射阶段 + 向量索引 |
| 抽取精度 | ⭐⭐⭐⭐ 高。两阶段各司其职，每阶段难度降低 |
| 运行成本 | ⭐⭐ 较高。每次入库增加一轮 LLM 调用 |
| Yuxi 兼容性 | ⭐⭐⭐ 中等。不动 LightRAG，在 inserter 后挂 hooks |

**优点**：不改 LightRAG，抽取和分类解耦；LLM 做分类映射比做抽取+分类更可靠。
**缺点**：增加一倍 LLM 调用成本（抽取一次 + 映射批处理一次）；延迟增加；两阶段之间可能积累错误。

**与当前方案 A 的关系**：当前方案的"策略 B 后置校验"本质上就是方案 D 的变体。两者可以互补——先用 A 做前置约束，再用 D 做兜底矫正。

---

#### 方案 E：原生语义推理引擎（OWL/RDF）

**做法**：用 W3C 语义网标准定义本体，用推理机自动推导实体类型、关系传递性和实例归属。

```
OWL 本体：
  Company ⊑ Organization
  worksFor(Person, Company) → worksFor(Person, Organization)   # 推理机自动推导
  
查询：
  "谁在组织工作？" → 自动召回 worksFor(x, Company) + worksFor(x, Government)
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐⭐⭐⭐⭐ 极高。需引入 RDF 三元组存储、OWL 推理机 |
| 抽取精度 | ⭐⭐⭐⭐⭐ 最高。逻辑推导保证一致性 |
| 运行成本 | ⭐⭐ 较高。推理计算量大，RDF 存储与 Neo4j 不兼容 |
| Yuxi 兼容性 | ⭐ 极低。当前 Neo4j + LightRAG 架构根植于属性图模型，完全不适配 RDF |

**优点**：逻辑严格、推导完备，适合医疗、金融等强合规场景。
**缺点**：工程复杂度极高；LightRAG 的实体抽取输出是属性图而非 RDF 三元组，转换成本大；推理机性能瓶颈。**不适合 Yuxi**。

**业界案例**：Palantir Foundry 的 Ontology 层本质上是个逻辑推理层，但它不依赖 OWL，而是自研了一套更轻量的类型系统——这也是我们更应参考的方向。

---

#### 方案 F：仅查询层本体增强

**做法**：不改造抽取管道，只在图谱查询时利用本体做检索增强（查询改写、标签展开、层级回退）。

```
用户查询："找所有组织"
  → 本体展开：组织={公司, 政府机构, 学校, NGO}
  → Cypher: WHERE label IN ['公司', '政府机构', '学校', 'NGO']
  → 如果没找到：回退到自由文本搜索
```

| 维度 | 评价 |
|------|------|
| 架构复杂度 | ⭐ 极低。只改查询适配器 |
| 抽取精度 | — 不影响抽取，标签质量保持原样 |
| 运行成本 | ⭐⭐⭐⭐⭐ 零额外成本 |
| Yuxi 兼容性 | ⭐⭐⭐⭐⭐ 完全兼容 |

**优点**：零风险，实施只需 1 天；能提升检索召回率。
**缺点**：**不改标签质量**——如果抽取阶段标注混乱，"苹果"一会是"水果"一会是"公司"，查询层没办法修复。只解决检索问题，不解决标签一致性问题。

### 10.3 综合对比矩阵

```
                    架构      抽取    运行    Yuxi    适合
                    复杂度    精度    成本    兼容性   场景
A. Prompt约束       ⭐⭐     ⭐⭐⭐   ⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 通用
B. Structured       ⭐⭐     ⭐⭐⭐⭐ ⭐⭐⭐   ⭐⭐     有库支持时首选
C. 微调模型         ⭐⭐⭐⭐  ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐      垂直领域
D. 两阶段映射       ⭐⭐⭐   ⭐⭐⭐⭐ ⭐⭐     ⭐⭐⭐   高精度需求
E. OWL/RDF推理      ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐     ⭐      强合规场景
F. 仅查询增强       ⭐      —       ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 快速验证
```

### 10.4 推荐方案：A + D 混合（即当前方案的完整形态）

结合 Yuxi 的架构约束（不改 LightRAG 库、属性图模型、通用平台定位），**A（前置 Prompt 约束）+ D（后置两阶段映射兜底）= 当前方案** 是最佳选择，原因是：

1. **架构匹配度最高**：不替换 LightRAG，不引入 RDF/OWL，利用 Neo4j 标签前缀做层级查询
2. **成本可控**：前置约束命中率高时不需要后置矫正；后置矫正只在抽取出错时触发，非全量执行
3. **渐进式落地**：查询层增强（方案 F）可作为 Phase 0 先上线验证本体价值，再逐步加入抽取约束
4. **保留升级空间**：如果未来 LightRAG 支持 Structured Output，可直接从方案 A 升级到方案 B

### 10.5 建议的渐进式路线

```
Phase 0（快速验证，1 天）→ 方案 F：查询层本体增强
  目标：验证本体对检索召回率的提升
  改动：仅 GraphAdapter + 一个 demo 本体用例

Phase 1-2（核心落地，5 天）→ 方案 A：Prompt 约束抽取 +
                              方案 D 兜底：后置校验映射
  目标：端到端本体标签写入
  改动：当前方案的主体内容

Phase 3（可选增强，按需）→ 方案 B：LLM Structured Output
  前提：LightRAG 支持 response_format 参数透传
  收益：将前置约束命中率从 ~70% 提升到 ~95%
```
