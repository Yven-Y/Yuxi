# 知识图谱图数据库与存储技术

> 整理日期：2026-05-28
> 目标：全面梳理知识图谱存储方案，对比主流图数据库选型

---

## 一、知识图谱存储方案概览

### 1.1 两种主流数据模型

| 模型 | 说明 | 代表格式/数据库 |
|------|------|----------------|
| **RDF 图模型** | 基于三元组的标准化语义网模型 | RDF、RDFS、OWL、SPARQL |
| **属性图模型** | 带标签和属性的节点和边 | Neo4j、NebulaGraph、JanusGraph |

### 1.2 两种模型对比

| 特性 | RDF 图模型 | 属性图模型 |
|------|-----------|-----------|
| 标准化程度 | 高（W3C 标准） | 低（各厂商独立） |
| 表达能力 | 强（支持本体推理） | 中（灵活易用） |
| 查询语言 | SPARQL | Cypher、Gremlin、GQL |
| 学习曲线 | 陡峭 | 平缓 |
| 适用场景 | 语义网、开放数据 | 企业应用、社交网络 |

## 二、基于关系的存储方案

在图数据库出现之前，知识图谱常使用关系型数据库存储。

### 2.1 三元组表（Triple Table）

```sql
CREATE TABLE triples (
    subject VARCHAR(255),
    predicate VARCHAR(255),
    object VARCHAR(255)
);

-- 示例数据
INSERT INTO triples VALUES ('张三', '就职于', '阿里巴巴');
INSERT INTO triples VALUES ('阿里巴巴', '总部位于', '杭州');
```

**优点**：简单直观
**缺点**：查询性能差（大量自连接）

### 2.2 水平表（Horizontal Table）

每个实体一行，每列一个属性：

```sql
CREATE TABLE person (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    age INT,
    company VARCHAR(50)
);
```

**优点**：查询简单
**缺点**：属性稀疏、 schema 不灵活

### 2.3 属性表（Property Table）

按实体类型分表：

```sql
CREATE TABLE person_properties (
    entity_id VARCHAR(50),
    property_name VARCHAR(50),
    property_value TEXT
);
```

**优点**：灵活扩展
**缺点**：查询复杂

### 2.4 六重索引（Six Indexes）

为三元组的所有排列组合建立索引：

```
SPO, SOP, PSO, POS, OSP, OPS
```

**优点**：任意模式查询都高效
**缺点**：存储开销大

## 三、原生图数据库

原生图数据库专为图数据设计，采用**免索引邻接（Index-Free Adjacency）**存储。

### 3.1 核心概念：免索引邻接

```
关系型数据库查询：
  查找张三的朋友的朋友
  → JOIN person_friends ON ...
  → JOIN person_friends ON ...
  → 时间复杂度随深度指数增长

图数据库查询：
  查找张三的朋友的朋友
  → 从张三节点出发，沿"朋友"边直接遍历
  → 时间复杂度随深度线性增长
```

## 四、主流图数据库详解

### 4.1 Neo4j

**定位**：最流行的原生图数据库

#### 核心特性

| 特性 | 说明 |
|------|------|
| **数据模型** | 属性图模型 |
| **查询语言** | Cypher（声明式，易读） |
| **存储引擎** | 原生图存储，免索引邻接 |
| **事务支持** | 完整 ACID |
| **扩展性** | 商业版支持集群，社区版单机 |
| **生态** | 最丰富，大量工具和集成 |

#### Cypher 查询示例

```cypher
// 创建节点
CREATE (p:Person {name: '张三', age: 30})
CREATE (c:Company {name: '阿里巴巴'})

// 创建关系
CREATE (p)-[:WORKS_AT]->(c)

// 查询：张三在哪个公司工作？
MATCH (p:Person {name: '张三'})-[:WORKS_AT]->(c:Company)
RETURN c.name

// 查询：张三的朋友的朋友
MATCH (p:Person {name: '张三'})-[:FRIEND*2]->(fof:Person)
RETURN fof.name

// 查询最短路径
MATCH p=shortestPath(
  (a:Person {name: '张三'})-[*]-(b:Person {name: '李四'})
)
RETURN p
```

#### 版本对比

| 版本 | 特点 | 适用场景 |
|------|------|---------|
| **社区版** | 免费、开源、功能完整 | 学习、开发、小型项目 |
| **企业版** | 集群、因果一致性、角色权限 | 生产环境、大规模应用 |

---

### 4.2 NebulaGraph

**定位**：国产开源分布式图数据库

#### 核心特性

| 特性 | 说明 |
|------|------|
| **架构** | 分布式（存储计算分离） |
| **查询语言** | nGQL（类 SQL） |
| **扩展性** | 水平扩展，支持千亿节点 |
| **性能** | 导入和查询性能优秀 |
| **可视化** | 内置可视化工具 Studio |

#### nGQL 示例

```ngql
// 创建图空间
CREATE SPACE IF NOT EXISTS test(vid_type=FIXED_STRING(30));

// 创建标签
CREATE TAG IF NOT EXISTS person(name string, age int);
CREATE TAG IF NOT EXISTS company(name string);
CREATE EDGE IF NOT EXISTS work_at(start_year int);

// 插入数据
INSERT VERTEX person(name, age) VALUES "p1":("张三", 30);
INSERT VERTEX company(name) VALUES "c1":("阿里巴巴");
INSERT EDGE work_at(start_year) VALUES "p1"->"c1":(2015);

// 查询
GO FROM "p1" OVER work_at YIELD dst(edge) AS company_id;
```

---

### 4.3 JanusGraph

**定位**：开源分布式图数据库，Apache 顶级项目

#### 核心特性

| 特性 | 说明 |
|------|------|
| **架构** | 分布式、可扩展 |
| **查询语言** | Gremlin（过程式遍历） |
| **存储后端** | Cassandra、HBase、BerkeleyDB |
| **索引后端** | Elasticsearch、Solr、Lucene |
| **事务** | 最终一致性 |

#### Gremlin 示例

```groovy
// 创建图
graph = JanusGraphFactory.open('conf/janusgraph-cassandra.properties')
g = graph.traversal()

// 添加顶点
zhangsan = g.addV('person').property('name', '张三').next()
alibaba = g.addV('company').property('name', '阿里巴巴').next()

// 添加边
g.addE('works_at').from(zhangsan).to(alibaba).property('since', 2015).iterate()

// 查询
g.V().has('name', '张三').out('works_at').values('name')

// 遍历：朋友的朋友
g.V().has('name', '张三').repeat(out('friend')).times(2).values('name')
```

### 4.4 其他图数据库

| 数据库 | 特点 | 适用场景 |
|--------|------|---------|
| **Dgraph** | 原生分布式、GraphQL+- | 云原生应用 |
| **TigerGraph** | 高性能、GSQL | 实时分析、大规模图计算 |
| **TuGraph** | 蚂蚁开源、高性能 | 金融风控、实时推荐 |
| **HugeGraph** | 百度开源、基于 JanusGraph | 安全、反欺诈 |
| **Galaxybase** | 国产商业、高性能 | 大规模企业级应用 |
| **ArangoDB** | 多模型（文档+图+KV） | 需要多种数据模型 |
| **OrientDB** | 多模型 | 复杂应用场景 |

## 五、图数据库选型指南

### 5.1 选型维度

```
                    数据规模
     小规模 ←────────────────────→ 大规模
     │                              │
单   │  Neo4j 社区版     Neo4j 企业版 │   分
机   │  ArangoDB         NebulaGraph │   布
     │  OrientDB         JanusGraph  │   式
     │                   TigerGraph  │
     │                   Galaxybase  │
     │                              │
     └──────────────────────────────┘
          简单查询 ←────────────────→ 复杂分析
```

### 5.2 具体建议

| 场景 | 推荐数据库 | 理由 |
|------|-----------|------|
| 学习/原型开发 | Neo4j 社区版 | 文档丰富，Cypher 易学 |
| 中小型生产项目 | Neo4j 企业版 / NebulaGraph | 稳定，生态好 |
| 大规模分布式 | NebulaGraph / JanusGraph | 水平扩展 |
| 实时图计算 | TigerGraph / TuGraph | 性能极致 |
| 多模型需求 | ArangoDB / OrientDB | 一库多用 |
| 国产替代要求 | NebulaGraph / TuGraph / Galaxybase | 国产化 |
| 云原生部署 | Dgraph / Neo4j Aura | 云友好 |

### 5.3 查询语言对比

| 语言 | 风格 | 代表数据库 | 学习难度 | 表达能力 |
|------|------|-----------|---------|---------|
| **Cypher** | 声明式 | Neo4j | 低 | 强 |
| **Gremlin** | 过程式 | JanusGraph | 中 | 极强 |
| **nGQL** | 声明式（类SQL） | NebulaGraph | 低 | 中 |
| **SPARQL** | 声明式 | RDF Store | 中 | 强 |
| **GSQL** | 图灵完备 | TigerGraph | 高 | 极强 |
| **GQL（ISO 标准）** | 声明式 | 未来标准 | 低 | 强 |
