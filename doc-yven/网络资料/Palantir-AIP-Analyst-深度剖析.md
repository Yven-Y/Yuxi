## 一、核心定位：AIP Analyst 是什么？

AIP Analyst 是一个**决策分析引擎 + 语义计算层 + Agent 驱动交互界面**的融合体。它承担的是从**数据理解 → 业务解释 → 决策建议 → 执行**的完整闭环能力。

本质上：

> **Analyst = Ontology 语义模型上的智能分析执行器 + 决策解释器**

也就是说，Analyst 在**业务语义层**做分析，而不是在数据层做分析。它不直接操作表，而是操作 `Customer（客户）`、`Order（订单）`、`Inventory（库存）`、`Supplier（供应商）` 等业务对象。

### Analyst vs BI 的本质区别

| 维度 | BI | AIP Analyst |
|------|-----|-------------|
| **数据模型** | 表 / SQL | Ontology（对象 + 关系） |
| **分析方式** | 报表 + 人工分析 | 自动分析 + Agent 推理 |
| **输出** | 图表 | 决策建议（Actionable Insight） |
| **交互** | Dashboard | 自然语言 + Agent |
| **闭环能力** | 无 | 有（可直接触发 Action） |

## 二、六套内置分析能力

Analyst 内置六套分析能力，自动化且可解释：

### 1. 描述性分析
- KPI 统计（均值/分位数/分布）、TopN / 排名、结构占比
- **输出示例**："华东区贡献收入 42%，但利润率低于均值 5%"

### 2. 诊断性分析
- 自动归因（Root Cause）、因子拆解（Driver Analysis）
- **输出示例**："利润下降的主要原因是：折扣率上升 + 高成本 SKU 占比提升"

### 3. 预测性分析
- 需求预测、收入预测、风险预测
- **输出示例**："未来 7 天库存缺口概率 68%"

### 4. 异常检测
- KPI 异常波动、行为异常（订单欺诈）、模式偏离
- **输出示例**："该客户订单利润波动 CV=0.92，高于行业 95% 分位"

### 5. 关联分析
- 图分析（客户-地址-订单）、路径分析、影响传播
- **输出示例**："多个账号共享地址，存在套利风险"

### 6. 决策分析
- What-if Simulation、优化（Optimization）、多方案推荐
- **输出示例**："建议从仓库 A 向区域 B 调拨 500 件，预计利润提升 12%"

## 三、工作原理：Agent 驱动的语义分析系统

**用户输入**：哪些客户是高利润但不稳定的？

**系统执行**：
1. Agent 解析意图
2. 调用 Ontology（Customer 对象）
3. 计算：`total_profit`、`profit_variance`
4. 筛选：`high_profit_unstable_flag = true`
5. 自动生成解释
6. 返回结果 + 推荐动作

**系统输出**：
- 发现 32 个客户：利润高、但订单波动大
- 给出建议：调整定价策略、优化 SKU 结构

### 分析 → 决策 → 执行的闭环

Analyst 并不是只分析，它可以直接触发：
- **Action（执行）**：补货、调拨
- **Workflow（流程）**：通知采购、生成审批单
- **Agent（自动处理）**：持续监控、自动响应

**示例**：Analyst 给出"库存 7 天后会缺货"的分析结果后，可直接触发补货 Action、生成调拨方案、通知采购。

## 四、完整分析工具集

AIP Analyst 内置了一套完整的分析工具集，覆盖从数据发现到可视化生成的完整链路。

### 第一类：Ontology 资源发现工具

| 工具名称 | 功能描述 | 使用场景 |
|---------|---------|---------|
| **Object Type Search** | 基于对象类型的元数据进行语义搜索 | 用户说"供应商" → 找到 Supplier/Partner/Vendor 等相关对象类型 |
| **Object Type Lookup** | 获取特定对象类型的完整元数据 | 确认某对象有哪些可查询字段 |
| **Object Search** | 在 Ontology 中进行全文搜索 | 搜索"Northampton"找到所有相关实体 |

### 第二类：数据选择、转换与过滤工具

| 工具名称 | 功能描述 | 底层实现 |
|---------|---------|---------|
| **Object Set** | 创建对象集合，支持过滤、图遍历、语义搜索 | Ontology Engine |
| **Object Lookup** | 获取特定对象的完整属性值 | Ontology API |
| **Ontology Aggregation** | 聚合计算（count/sum/avg/min/max/percentile/stddev） | Ontology Engine |
| **Ontology SQL** | 对对象集执行 SQL 查询，可链式输入 | SQL-on-Ontology |
| **Dataset SQL** | 直接对底层数据集执行 SQL，绕过 Ontology 层 | Dataset-level SQL |

### 第三类：可视化工具

| 工具名称 | 功能描述 |
|---------|---------|
| **Create Visualization** | 使用 Vega 图表构建交互式图表 |
| **Map Visualization** | 对地理空间数据进行地图可视化 |

### 第四类：上下文与配置工具

| 功能 | 说明 |
|------|------|
| **Context Management** | 手动/自动管理会话上下文 |
| **Branching（分支）** | 在任意分析节点分叉，创建新标签页并行探索 |
| **Scope Limiting** | 限制搜索范围到特定 Ontology 和对象类型组 |
| **Pre-load Context** | 启动时自动加载预设上下文 |

## 六、Provenance 追踪机制（反幻觉）

AIP Analyst 最关键的设计之一是 **Provenance 追踪机制**，用于解决幻觉挑战。

**实现方式**：
每次分析生成一个"有向图"：
- **节点** = 分析步骤（工具调用 + 输入参数 + 输出结果）
- **边** = 步骤间的数据依赖关系

**用户可查看**：
1. **追踪推理路径**：每一步用了什么数据？
2. **审计数据转换**：数据经过了哪些处理步骤？
3. **验证真实性**：结论基于哪些实际 Ontology 对象？
4. **可重现性**：给定相同输入，是否能重现相同结果？

**分析大纲**：
- 用户消息 → 圆形图标
- 工具调用 → 对应功能的图标
- 每个工具调用附带 Token 消耗统计
- 可隐藏特定工具结果以简化视图

## 七、两种工具调用模式

### Prompted Tool Calling（提示词式工具调用）

在 Prompt 里用文字告诉大模型有哪些工具、怎么用、什么时候调用、参数格式是什么。

**优点**：通用性强，几乎所有大模型都可以使用。

**缺点**：
- 模型需要阅读大量工具说明，工具越多 Prompt 越长
- 容易出现格式错误（JSON 不合法、字段名写错）
- 复杂任务需要多轮往返，串行执行

### Native Tool Calling（原生工具调用）

模型或平台本身就支持工具调用协议，以结构化 schema 的方式注册给模型。

**优点**：
- 工具定义结构化传入，token 使用更少
- 模型输出结构化 tool call，后端更容易解析
- 支持并行工具调用

**对比总结**：

| 维度 | Prompted Tool Calling | Native Tool Calling |
|------|----------------------|---------------------|
| **机制** | 靠提示词模拟工具调用 | 模型原生理解工具调用 |
| **适用范围** | 广（所有能看懂文本的模型） | 受限（需模型和平台原生支持） |
| **性能** | 较慢（多轮往返） | 更快（可并行） |
| **稳定性** | 较低（格式易出错） | 较高（结构化协议） |
| **适用场景** | 原型验证、临时工具、开源模型 | 企业级 Agent、数据查询、业务执行 |

**企业级结论**：Native Tool Calling 更适合企业级 Agent，因为它把工具调用从自然语言文本变成平台协议，降低了模型自由发挥导致的错误。

## 八、三类检索上下文（Context）

AIP Analyst 支持三类检索上下文，这是其区别于普通 Chatbot 的核心能力。

### 1. Ontology Context（本体上下文）

从企业 Ontology 中检索相关业务对象，提供给大模型分析。

**两种典型方式**：
- **语义搜索相关对象**：用户提问后，系统根据语义搜索找到最相关的 Ontology 对象
- **传入固定对象集合**：用户已在界面上选中某些对象，直接传给模型分析

**适用场景**：分析某个客户、某批订单、某个销售员、某个供应商等。

**优势**：上下文来自 Ontology，结构化、可追溯、贴近业务语义。

### 2. Document Context（文档上下文）

从非结构化文档（PDF、Word、合同、政策文件等）中提取文本内容。

**两种主要方式**：
- **全文模式**：整篇文档文本放进上下文（适合短文档）
- **相关片段模式**：文档切片后向量检索 Top-K 片段（典型 RAG）

**适用场景**：合同风险分析、政策条款解读、技术文档问答、会议纪要总结等。

### 3. Function-backed Context（函数支持的上下文）

通过用户自定义函数动态计算、组合、过滤、排序后生成上下文。

**适用场景**：
- 先查客户，再查订单，再查合同，再查风险事件
- 先做关键词匹配，再做语义搜索，再按业务权重排序
- 只返回当前用户有权限访问的数据
- 跨多个系统组合上下文

**核心区别总结**：

| Context 类型 | 数据来源 | 检索机制 | 适用场景 |
|-------------|---------|---------|---------|
| **Ontology Context** | 企业 Ontology（结构化业务对象） | 对象检索、语义搜索 | 业务对象明确的结构化分析 |
| **Document Context** | 非结构化文档 | 全文注入或向量检索 Top-K | 合同、报告、制度分析 |
| **Function-backed Context** | 任何系统 | 自定义函数组合多种检索 | 跨系统、复杂过滤、多源检索 |

**关键洞察**：企业级 Agent 的核心不是模型有多聪明，而是**上下文是否正确、完整、可追溯**。

## 九、高级功能

### 分支分析（Branching）

在任意分析节点"分叉"，创建新标签页——从相同起点探索不同分析路径，各分支独立运行。

**价值**：
- 分析过程从"线性"变为"树状"，支持并行探索多个假设
- 每个分支是独立会话，不会互相干扰

### 内联引用标注（Citations）

分析摘要回复中包含内联引用标注，直接链接到生成该结论的具体工具结果。

**示例**：
> "Q3 收入较 Q2 下降了 12%，主要原因是华东区域收入下降了 18%（[1][2][3]）"
> - [1] = Ontology Aggregation 结果：华东 Q3 SUM(revenue) = 4.2M
> - [2] = Ontology Aggregation 结果：华东 Q2 SUM(revenue) = 5.1M
> - [3] = Ontology SQL 结果：按区域聚合的 Q2→Q3 变化率

### 事件驱动型分析

AIP Analyst 作为 Workshop Widget 嵌入业务应用时，支持事件驱动：
- 在销售仪表盘中，选中某区域 → 自动分析该区域收入驱动因素
- KPI 告警触发时 → 自动对异常指标进行根因分析
- 用户在地图上点击某城市 → 自动展示市场分析摘要

### Context Cleanup（上下文清理）

自动管理长会话中的上下文膨胀问题：
1. 识别过时的/不必要的历史信息
2. 将其标记为"隐藏"
3. 保留完整记录（用户仍可在 Analysis Outline 中查看）

## 十、多维能力特征总结

### 1. 分析范式
**自然语言 → Ontology 遍历 → 多步推理**

AIP Analyst 不是简单地把自然语言转换成 SQL，而是：
自然语言问题 → 理解业务对象 → 定位相关 Ontology 对象 → 沿着对象关系遍历 → 查询对象属性和关系数据 → 必要时执行 SQL 聚合 → 多步推理 → 输出结论、证据和可视化

### 2. 分析深度
**Ontology 多跳推理 + SQL 聚合 + 可视化**

- **多跳推理**：客户 → 订单 → 产品 → 供应商 → 交付延迟 → 客户投诉
- **SQL 聚合**：sum、avg、count、percentile、variance 等
- **可视化**：柱状图、折线图、饼图、散点图、热力图、地图等

### 3. 推理透明度（极高）

- **Provenance Graph**：证据溯源图，展示用了哪些数据对象、查询了哪些数据集
- **Analysis Outline**：分析大纲，展示模型一步步分析的路径
- **Citations**：引用或证据链接，每个结论关联到具体数据

### 4. 语义层深度（极深）

深度绑定 Palantir 的 Ontology 体系：
- **Object**：业务对象（客户、订单、产品等）
- **Link**：对象关系
- **Interface**：对象能力的抽象层
- **Action**：可执行动作
- **Property**：对象属性
- **Metric**：对象指标
- **Security**：权限控制

### 5. 多 Agent 协作（原生支持）

不同 Agent 负责不同任务：
- 销售分析 Agent：分析销售额、客户、订单、利润
- 供应链 Agent：分析库存、供应商、交付风险
- 财务 Agent：分析回款、现金流、毛利率

### 6. 嵌入与编排

- **Workshop Widget**：嵌入到业务应用界面
- **事件驱动**：由界面事件、业务事件触发分析

## 十一、与普通工具的本质区别

| 对比维度 | 普通 BI Copilot | 普通 Chatbot | AIP Analyst |
|---------|----------------|-------------|-------------|
| **核心围绕** | 表、指标、图表 | 语言模型生成回答 | 业务对象、关系、动作、证据链 |
| **数据基础** | SQL 查询 | 预训练知识 | Ontology、SQL、数据证据、分析步骤 |
| **输出** | 图表 | 文本 | 决策建议 + 可视化 + 证据溯源 |
| **闭环能力** | 无 | 无 | 分析 → 决策 → 执行 |

## 总结

> **Palantir AIP Analyst 的野心不是做一个"能聊天的 BI"，而是构建一个基于企业 Ontology 的"业务世界分析推理层"——让 AI 在正确的上下文里，围绕真实的业务对象进行可溯源、可执行的分析。**

AIP Analyst 更像是一个**企业业务世界里的分析推理层**，而不是一个简单的问答入口。
