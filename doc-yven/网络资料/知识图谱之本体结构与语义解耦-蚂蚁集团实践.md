## 简介

过去两年多的时间，针对蚂蚁域内业务场景和知识体系多样、复杂，知识建模成本高导致图谱项目启动难的问题，我们提出了一种**结构与语义解耦的知识建模及 schema 设计方法**，并在商家图谱、事理图谱、保险图谱等多个项目中进行实践。相关简化 schema 设计及帮助对知识的属性语义化、标准化的能力已经集成到蜘蛛知识平台。

本文总结了过去的工作，沉淀为体系化的方法论，并针对不同复杂程度的知识建模问题，进行实操指南。

## 背景

### 知识建模的定义

知识建模是解决将真实世界中的海量信息转化为符合计算机处理模式的结构化数据，其中包括对真实世界中事物的属性特征及其关系的共性的抽象，制定表示的规范，同时兼顾对常识或领域概念及概念层级体系的语义理解，即体现了对知识的认知过程。

### 知识建模方法对比

| 方法 | 特点 |
|------|------|
| **关系型数据库** | 用实体及其属性对数据结构化，不包括语义的建模，容易存在大量数据冗余，多跳跨表查复杂、效率低 |
| **知识工程** | 本体表示：将知识表示为逻辑符号的形式；框架表示：强调 slot-value 结构化。弊端：人工构建成本太高 |
| **语义网** | 出发点是用文档中的数据关联+逻辑描述，让计算机理解世界。但语义完备性成为逻辑学家的游戏，无法工业化落地 |
| **知识图谱** | 以 SPO 三元组表示实体间事实关系；但 SPO 对多元关系表示存在缺陷；schema 设计主观导致异构 |
| **事理图谱** | 将事件及事件关系抽取并抽象，构建描述事件演化规律和模式的事理逻辑知识库 |
| **常识概念图谱** | 围绕常识性概念建立的实体及关系，帮助自然语言文本理解 |
| **知识超图** | 超图：每个边可包含两个以上的点，解决多元知识的表示 |

### 蚂蚁域内常见建模问题

| 建模问题 | 现有解决方案及不足 |
|---------|------------------|
| **商家资产等实体-关系 schema 设计** | schema 设计启动难，难以决策属性/关系的设计、实体类型的划分；设计主观导致不同图谱间知识异构 |
| **常识、领域结构化语义理解** | 数据结构定义和语义建模的耦合，导致工程实现及维护管理的复杂性 |
| **跨图谱融合场景** | 不同业务部门构建图谱时先专注自身领域，但需要引入其他领域知识；需要统一 schema 规范 |
| **保险、黑产等业务逻辑表达需求** | 需要支持业务规则、专家经验的形式化表达及推理能力；一阶谓词、dsl 对用户有门槛 |
| **用户行为建模场景** | SPO 三元组表达多元关系是有损的；超图结构对非算法用户有学习门槛 |
| **事理图谱及事理关系建模** | 已有的研究只解决了特定一类的表示，蚂蚁场景需要对从实例到概念、从事实到常识的整体架构 |

## 方案概述

### 核心观点

**"本体"在知识图谱建模阶段存在误用。知识图谱建模，不需要"本体"，而应该关注数据结构上的"元数据"的定义，以及知识语义关联的标签概念体系及概念网络。**

### MOF 四层元模型框架

基于 MOF（Meta-Object Facility）四层元模型框架，提出知识认知建模方法论：

| 层级 | 名称 | 说明 | 示例 |
|------|------|------|------|
| M3 | 元元概念 | 所定义的建模规范 | 实体、概念、关系等建模要素 |
| M2 | 元概念 | 定义实体类型的 schema | "商家 schema"、"事件 schema" |
| M1 | 概念 | 对实体的语义细分 | "蚂蚁商家"、"外卖商家"、"白酒板块事件" |
| M0 | 实例 | 现实中具体的事实 | id 为 2088xxxx 的 A 空间肯德基商户 |

### 方案价值

1. 提供统一的数据结构抽象及本体语义建模方法论，规范图谱"设计模式"
2. 提出概念语义建模框架，将知识的结构化表示与语义常识建模解耦
3. 定义核心实体 schema 及沉淀通用语义概念体系，帮助解决多元异构知识的跨域融合
4. 定义多元关系、逻辑规则、事理关联的建模方法，满足复杂业务场景知识表达需求

## 基础篇：实体关系设计

### 解决问题

解决数据的结构化表示，包括实体各属性字段的规范定义，及设计实体间的关系，以便将数据最终构建为有别于传统数据表的图结构形式，便于基于路径的多跳关系查找。

### 适用场景

- 业务场景关注于静态的、体现物理世界或业务流中客观存在的"事实知识"
- 已有结构化数据为主（实体表、关系表、用户行为数据等）的数据资产
- 业务对实体的类型存在划分，且细分类是有限的（一般只有两三种）
- 业务对实体特定属性有枚举描述，但不需要基于属性传播

### 术语定义

#### Schema

Schema 是知识的"元数据"表达方式，定义了知识的概念的属性、关系、属性及约束。主要实现了实体的结构化和实体间的关系的定义。

#### 实体

物理世界或数字世界存在的事物是一个实体，实体对应于数据表中的一行记录。

**实体类型**：即实体的"schema"。它是对具有共同数据结构（特征）的一类数据实例的"元数据"模式定义。

**自然人模型（Person）示意**：

| 属性英文名 | 属性中文名 | 属性类型 | 属性值 | 是否必填 |
|-----------|-----------|---------|--------|---------|
| id | id | String | 12345xxx | 是 |
| name | 姓名 | String | 张三 | 是 |
| certId | 证件号 | String | 330121xxx | 否 |
| certType | 证件类型 | 枚举类型 | 身份证 | 否 |
| birthday | 出生日期 | 时间类型 | 20230215 | 否 |
| gender | 性别 | String | 男 | 否 |
| occupation | 职业 | String | 白领 | 否 |

#### 关系

描述实体-实体间的关联。在基础的实体关系设计时，只考虑满足 SPO（Subject-predicate-Object）表示的二元关系。

**自然人相关关系定义**：

| Subject | Predicate | Object | 是否唯一 |
|---------|-----------|--------|---------|
| Company | 法人 | Person | 是 |
| Person | 好友关系 | Person | 否 |
| Person | 夫妻关系 | Person | 是 |
| Person | 居住地 | POI | 否 |

### 属性语义标化

#### 属性 vs 关系的抉择困境

在实体-关系建模时，对于实体的特性字段，到底应该建模为属性，还是应该将特征 key 构建为关系，特征值建模为实体，设计者经常陷入两难。

**属性的特点**：易维护（值覆盖）、存储量小、不传播，难以发现关联
**关系的特点**：有维护成本（修改需要删边再拉边）、储存量大、可传播，但同关系类型的边过多会造成"热点"

#### 属性标化方案

为解决上述困境，提出基于**属性语义标化**的建模方法：

- 用户在实体建模时，不必纠结实体特征需要定义为属性 or 关系，**统统建模为属性**
- 在属性类型选择时，除了 int、float、text 三种基本类型外，提供具有**语义传播能力**的语义类型
- 在实例数据生产时，用户当作属性维护
- 根据所选择的属性语义标化类型，系统自动构建"**虚拟边**"
- 系统自动创建及维护的虚拟边，在查询效率、图算法邻边采样时，与用关系建模的物理边效果一致

**属性语义标准化类型**：

| 属性类型 | 类型细分 | 说明 |
|---------|---------|------|
| **内置类型-概念类型** | 通识概念 | 覆盖 17 个大类的 2W+ 常识概念 |
| | 行业类目 | MCC 类目、POI 类目、门店类目等 |
| **内置类型-标准语义类型（编码 id 相关）** | 虚拟地址 | 邮箱、网址、手机号码、Mac 地址等 |
| | ID 属性 | 身份证号码、2088 账号、支付宝 PID、银行账户等 |
| **内置类型-标准语义类型（时间相关）** | 时间戳 | 时间标准化及计算比较 |
| | 时间区间 | [起始时间, 结束时间] |
| | 时间间隔 | 一天、一年、24 小时等 |
| **内置类型-标准语义类型（空间类型）** | 行政区划 | 国家-省-市-区四级 |
| | 经纬度坐标点 | (经度, 纬度) |
| | 经纬度范围 | 地理区块四边形 |
| **自定义属性类型** | 实体/概念 | 用户自定义的实体类型或概念类型 |

### 建模步骤及案例

#### 1. CoreKG schema 复用

从过去的业务图谱设计经验中，总结了蚂蚁场景下常见的实体类型 schema，并沉淀到 CoreKG 核心图谱。当业务涉及这些实体数据时，可以直接引用/复用。

#### 2. 实体关系设计

参考 CoreKG 中已有实体的 schema，针对业务问题及数据，构建业务所需实体定义。

**支付宝用户模型（AlipayUser）示意**：

| 属性英文名 | 属性中文名 | 属性类型 | 属性值 | 是否必填 |
|-----------|-----------|---------|--------|---------|
| id | AlipayId | 编码类型 | 2088 | 是 |
| name | 姓名 | String | 张三 | 否 |
| memLevel | 会员等级 | 枚举类型 | 黄金会员 | 否 |
| shoppingPref | 购物偏好 | 物品概念 | 小吃 | 否 |

对于不同业务实体归属同一主体的情况：
- 可以在 Schema 层归类到统一实体模型上（深度继承）
- 可以在数据层在相同实例之间增加 isA 或 sameAs 谓词关系（实体融合）

#### 3. 语义标准化

将可以标化的属性选择为标准属性类型，对于适用 id 链指/概念链指的关系，转化为语义属性。

## 进阶篇：概念语义建模

### 解决问题

将语义建模与知识的结构化表示解耦，用"概念语义建模"来对常识概念及常识关系建模，对特定领域知识的认知体系和经验规则建模。

### 适用场景

- 希望对业务逻辑、领域经验进行管理；对文本属性不只是作为"符号"，还希望理解文本背后的语义
- 业务上对实体定义了非常详细的分类类目，且以树状形式组织
- 实体的属性字段的值是行政区划、职业、行业类型等常识术语，希望这些属性在图上"可传播"
- 业务定义的类目存在背后的定义逻辑（如：活跃人群 = 过去 30 天支付宝访问超过 1 次的 user）
- 希望表达领域常识（程序员有夜间出行偏好）并应用

### 术语定义

#### 概念

把所感知的事物的共同本质特点抽象出来，加以概括，是思维的基本形式之一，反映客观事物的一般的、本质的特征。

**什么应该被定义为概念**：
- **类目概念**：对具有同样特征的一类实体的语义抽象（业务类目、领域 taxonomy）
- **常识概念**：在特定领域下，人们有共识的无歧义短语（杭州市、手机、中秋节）
- **原子概念**：L0-L2 级的概念，概念名是不可拆分的表达完整语义的核心词
- **复合概念**：在一个核心词概念上增加语义修饰限定（如"白酒产品价格上涨"、"杭州互联网上市公司"）

#### 元概念

Meta-concept，即概念的概念。在蜘蛛上是指用来组织一个特定概念体系的规范。元概念定义就是根据对特定领域/业务的认知或常识，定义该类型概念的结构，约定概念的属性、层级结构及表达层级结构的语义谓词。

#### 概念 vs 实体

| 维度 | 概念 | 实体 |
|------|------|------|
| **定义** | 对具有同样特征的实例的抽象，是语义上/认知上能够被"归类"为同一类型的实例的集合 | 对拥有同样数据结构/论元要素的数据的定义；是 id 化的、唯一存在的实例 |
| **特性** | 符号化的、领域内共识的、语义相对恒定的 | 客观存在、特征动态变化、拥有特异的属性/关系 |
| **属性** | 可以先认为"概念"是没有"属性"的（除了编码、别名、描述） | 拥有特异的属性/关系定义 |

### 建模步骤及案例：事件体系语义建模

#### 1. 定义实体类型 schema

对于事件的结构化表示，先构建一个定义所有事件共有事件要素的 schema：Event。

#### 2. 建立实体类型对应的元概念

用概念建模来定义实体的细分类体系。对于事件的分类体系，定义 EventConcept 作为元概念。

#### 3. 为实体类型 schema 设置专属分类体系

建立 `Event - belongTo -> EventConcept` 的关系，定义了 Event（及其子类型）的实例由 EventConcept 为 Root 的概念体系做细分类。

#### 4. Schema 的结构细化

通过 schema 的继承，定义子类的事件 schema 及增加要素定义。如 CompanyEvent 增加了"涉事公司"，LivestockEpidemicEvent 增加了涉事牲畜、牲畜死亡规模、疾病类型等。

#### 5. 实例生产

- **非结构化数据**：基于 schema 约束的信息抽取，并将抽取到的信息标准化后填充
- **结构化数据**：对 ODPS 表和实体类型 schema 的知识结构映射，完成数据实例化及入图谱

#### 6. 语义网络构建

每个概念体系本身是树状结构，但概念之间还可能存在丰富的常识语义关联。

### 通用常识语义建模

基于对蚂蚁内部常见主体及其相关类目、属性字段的分析，并参考百科词条分类体系、Hownet、termtree 体系，定义了覆盖 17 个"元概念"类型的常识知识树的主干框架。

**层级结构**：
- **L0-元概念（概念类型）**：对应为实体类型（品牌、术语、事件、组织机构等）
- **L1-概念分型的模式**：决定概念类目细分的方式
- **L2-Ln-类目细分**：概念类型在确定子领域/场景下的细分

### 保险语义网络建模

保险产品图谱将保险业务中对保险产品的业务分类类目、领域标准分类、保险产品的各个重要特性建模，并将业务自定义的产品标签概念背后关联的产品特性、产品分类的逻辑固化到图谱中。

### 意图语义网络建模

**意图图谱**的核心本体主要共包含**四类节点**（意图、功能词、产品词、义原）和**三类关系**（isA、Consist、Has）。

- "意图"描述了用户需求背后的动机，主要由一个功能动词和一个产品实体组成动宾结构
- "功能动词"和"产品实体"可以用更细粒度的 Hownet 义原表示

## 高阶篇：多元关系架构

### 术语定义

#### 多元知识

根据论元个数把关系分为：一元关系、二元关系和多元关系。

- **一元关系**：表示实体/概念的性质、属性等（有翅膀(鸟)）
- **二元关系**：表示两个实体之间的关系（中国-首都->北京）
- **多元关系**：多个论元共同决定的事实

#### 超图

超图（Hypergraph）是一种更加抽象的图，与传统图的区别主要在于超边可以同时包含多个（>2）结点。超图通过引入超边关系，能够完整表达各种复杂的关系类型。

#### 事件

事件是加入时间、空间，区分行为主体、客体的实体类型。事件类型对实体类型补充了**"随时空动态变化"的信息和"事物发展的规则"**（因果、顺承等关系），是一种多元知识。

#### 概念的内涵与外延

- **内涵**：反映在概念中的对象的本质属性或特有属性
- **外延**：具有概念所反映的本质属性或特有属性的对象，即概念的适用范围

### 解决问题

现实中的事件、规则、场景知识是多元关系。传统图谱三元组表示可能是有损的转换。提出兼容与超图结构互相无损互转的时空行为事件表示方法：

**将时空多元关系（即事件或行为）本身抽象为一个事件节点，并定义事件节点与其各事件要素间的关联。事件节点本身即为超边的具像化，能够在 SPO 表示与超图表示间进行结构化知识的无损转换。**

### 适用场景

- **多元时空事件**：对用户行为、金融事件、保险理赔、业务流程等提供简洁而统一的建模范式
- **概念的语义定义**：定义概念的等价逻辑规则，帮助具体业务场景下的知识决策管理
- **多视角的知识建模架构**：从实例到概念、从事实到常识的整体架构

### 事件表示框架

对多元时空行为事件定义了统一的建模框架，将事件的属性分为：

| 要素类型 | 事件要素 | 解释 | 值类型（实体） | 值类型（概念） |
|---------|---------|------|--------------|--------------|
| **基本要素** | id | 事件唯一 id | - | 概念事件的名称即为其 id |
| | name | 事件标题 | - | - |
| | description | 事件描述摘要 | - | - |
| **时间要素** | happenTime | 发生时间 | 年份、时间点 | 时间段标签、特殊节日概念 |
| | startTime | 起始时间 | - | - |
| | endTime | 终止时间 | - | - |
| **空间要素** | happenLoc | 发生位置 | 经纬度坐标点、POI、AOI | 行政区划概念 |
| | startLoc | 起始位置 | 经纬度坐标点、POI、AOI | - |
| | endLoc | 终止位置 | 经纬度坐标点、POI、AOI | - |
| **主体要素** | eventSubject | 事件主体 | uid、公司 id 等 | 公司类型、品类等概念 |
| **客体要素** | eventObject | 事件客体 | 产品、门店、小程序等 | 品类、基金板块等 |
| | intent | 行为意图 | - | 意图概念 |
| | behavior | 行为类型 | 交易/搜索/点击/使用/出行 | 交易/搜索/点击/使用/出行 |

### 概念语义定义

#### 事件概念管理

通过对实体分类体系和领域知识/常识中的通用语义元素的定义，以树状层级体系进行组织，自顶向下的体现实体语义的细分。

**概念建模相关语义谓词定义**：

| 谓词定义 | 谓词语义 | 举例 |
|---------|---------|------|
| 实体类型 - belongTo -> 概念 | 该实体类型下的实例可以被分类为以 c 为根结点的子树上的概念 | EL.Event - belongTo -> EventConcept |
| 实体实例 - belongTo -> 概念 | 该实体属于概念所指的 grained type | x年x月alibaba股价上涨 5% - belongTo -> 股票价格上涨事件 |
| 概念 - isTypeOf -> 元概念 | 一个元概念下的概念，都是该体系下的类型 | 趋势事件 - isTypeOf -> 事件概念 |
| 概念 - 特定语义 -> 概念 | 定义概念上下层级间的语义关系 | 股票价格上涨事件 - isA -> 价格上涨事件 |

#### 概念事件的逻辑语义

对于"分类概念"，支持定义等价的逻辑表达式，定义该概念的语义内涵。当概念定义了逻辑表达式后，可以根据逻辑表达式进行双向推理：

- **基于规则的实例细分**：当算法分类只分到较粗粒度，可以使用逻辑表达式根据实例数据各属性/关系的值，帮助推断出实例的细分类型
- **一致性检测**：对于已知所属概念细类的实例，用逻辑规则帮助检验其各字段属性是否满足概念的定义

**示例**：
```
汽车整车销量事件（Concept） <=>  
if s isInstanceOf IndustrialChainEvent  
and s.产品 == 汽车整车 and s.指标 == 销量
```

#### 概念演化挖掘

在具体业务场景中，概念类目树随着业务语义的细分可能无限膨胀。提出基于实例统计的概念自动生成方法：

1. **对产业链事件设置分类层次**（自顶向下类型细分的优先级）：涉事指标 -> 发生趋势 -> 发生幅度 -> 涉事产品 -> 事件状态
2. **定义概念事件生成命名模版**：[产品][指标][事件状态][幅度][趋势] + '事件'
3. **基于实例的统计对概念细分**，并注意剪枝避免概念树过于庞大

### 多元时空认知架构

综合使用实体关系建模、概念语义建模及事件行为的多元关系定义，主要用于事理图谱、用户行为等场景。

**三个层面**：

1. **模式层**：定义知识的结构化表示（schema）、语义规则、事理关系
2. **概念层**：定义知识的语义认知体系，及对业务中所涉及的常识或特定领域术语的概念体系建模
3. **实例层**：受模式层的约束，对非结构化文本做信息抽取；受概念层的语义约束，标准化、语义化为规范的属性值表示

**核心设计**：

- 多元时空知识可包含多元时空事件实体以及多元时空概念事件
- 可以将多元知识建模为一个"超边"节点，体现其多个论元要素的关联
- 多元知识节点实例之间可以具有边连（顺承、因果、伴随、组成）
- 通过对多元时空行为知识的概念化，有助于进一步挖掘多元知识中的规律，进行信息预测

**工程优化**：

由于事件间的语义关系是难以穷尽的，在工程实现上，并不对事件间的同主体、同时间、同地点等关系边做物理存储，而是基于查询条件进行图采样，并实时或按需进行语义化计算确定采样结果中各事件间的语义边，有效避免了图谱中边"爆炸"的问题，节约了存储空间。

## 未来展望

在大模型的冲击下，知识图谱与大模型的融合成为一个有意义的探索方向。图谱本身是对数据/文本的压缩，通过知识建模定义的知识的结构规范，提炼出知识最本质的特征和语义。因此，schema 本身可以作为一种强范式的 instruction。

尝试了在三个方向上图谱结构化数据与大模型的互动：
1. **知识建模**：让大模型帮助自动生成常识知识的 schema 定义
2. **知识抽取**：以 schema 作为 prompt 约束，生成高质量的结构化知识
3. **知识探测**：结合大模型和 in-context learning 进行知识发现

## 核心方法论总结

1. **结构与语义解耦**：将知识的结构化表示（schema）与语义认知（概念体系）解耦，降低认知复杂度和工程实现难度
2. **属性语义标化**：统一用属性建模，通过语义类型自动构建虚拟边，兼顾维护便利性和图传播能力
3. **MOF 四层元模型**：元元概念 -> 元概念（schema）-> 概念 -> 实例，串联知识建模、生产、管理应用的全生命周期
4. **多元关系表示**：将事件抽象为超边节点，实现 SPO 与超图的无损互转
5. **概念逻辑语义**：通过等价逻辑表达式定义概念的内涵，支持双向推理和一致性检测
